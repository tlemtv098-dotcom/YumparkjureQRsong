# สคริปต์พรีเซนต์ — อ่านตามนี้ได้เลย

> เวลารวม ~10-12 นาที ไม่รวมสาธิตสด (สาธิตใช้สคริปต์อีกไฟล์ `docs/demo-rehearsal.md`)
> พูดช้า ๆ ชัด ๆ ติดตรงไหนข้ามไปก่อน กลับมาเก็บตอนตอบคำถามได้

---

## สไลด์ 1 — ปก (~20 วิ)

"สวัสดีครับ ผมนายสุภวัฒน์ จันไพจิตร รหัสนักศึกษา 671320101 ครับ
โครงงานของผมชื่อ ระบบจูเกะซ์ร้าน KPP ครับ เป็นเว็บให้ลูกค้าร้านขอเพลงได้เองจากโทรศัพท์
เว็บจริงรันอยู่ที่ลิงก์บนสไลด์นี้เลยครับ เปิดดูได้ตลอด"

## สไลด์ 2 — ปัญหา (~45 วิ)

"เริ่มจากปัญหาก่อนครับ มี 3 ข้อ
ข้อแรก ลูกค้าต้องเดินมาขอเพลงที่เคาน์เตอร์ ทำให้คิวช้า
ข้อสอง เครื่องจูเกะซ์ทั่วไปเพลงน้อย ปรับรายการไม่ได้
ข้อสาม เจ้าของร้านไม่รู้ว่าลูกค้าชอบเพลงอะไร
เป้าหมายของผมเลยมี 2 อย่างครับ คือให้ลูกค้าขอเพลงเองได้จากโทรศัพท์
และให้เจ้าของร้านเห็นความนิยมเป็นกราฟครับ"

## สไลด์ 3 — บทบาทผู้ใช้ (~45 วิ)

"ระบบมีผู้ใช้ 3 ระดับครับ
admin ทำได้ทุกอย่าง จัดการผู้ใช้ แนวเพลง แท็ก ดูแดชบอร์ด ส่งออกข้อมูล
staff จัดการคิวเพลงกับเพลย์ลิสต์
customer ขอเพลงกับจัดการเพลย์ลิสต์ของตัวเอง
จุดสำคัญคือผมตรวจสิทธิ์ที่ฝั่งเซิร์ฟเวอร์ด้วยฟังก์ชันชื่อ role_required
ไม่ใช่แค่ซ่อนปุ่มหน้าจอ หมายความว่าถึงจะพิมพ์ URL ตรง ๆ เข้ามา ถ้าสิทธิ์ไม่ถึงก็เข้าไม่ได้ครับ"

## สไลด์ 4 — สถาปัตยกรรม (~45 วิ)

"เทคโนโลยีที่ใช้คือ Django 6 กับ Gunicorn 2 workers เสิร์ฟไฟล์ static ด้วย WhiteNoise
โครงสร้างเป็นแบบมาตรฐานของ Django เลยครับ โมเดล ฟอร์ม วิว เทมเพลต
หน้าจอใช้ Tailwind CSS
ฐานข้อมูลตอนนี้ใช้ Postgres ครับ — **(โน้ต: สไลด์เขียนว่า SQLite อันนั้นข้อมูลเก่า ผมย้ายไป Postgres แล้ว พูดตามนี้)**"

## สไลด์ 5 — ER Diagram (~30 วิ)

"รูปนี้คือความสัมพันธ์ของตารางครับ รายละเอียดอยู่สไลด์ถัดไป"

## สไลด์ 6 — โมเดลหลัก (~1.5 นาที — จุดที่อาจารย์ถามเยอะสุด)

"โมเดลมี 9 ตัว ผมขออธิบายความสัมพันธ์ 4 แบบที่ใช้ครับ
แบบแรก One-to-One: Profile ผูกกับ User คนละหนึ่งแถว เก็บ role
และมี signal สร้าง Profile อัตโนมัติทุกครั้งที่มี User ใหม่
แบบที่สอง One-to-Many: เพลย์ลิสต์มีเจ้าของเป็น User ผ่าน ForeignKey
ลบ User แล้วเพลย์ลิสต์ของเขาหายตามไปด้วยเพราะตั้ง on_delete แบบ CASCADE
แบบที่สาม Many-to-Many ธรรมดา: เพลย์ลิสต์กับแนวเพลง เพลงกับแท็ก
แบบที่สี่ Many-to-Many ผ่านตารางกลางชื่อ PlaylistSong
ที่ต้องมีตารางกลางเพราะผมอยากเก็บลำดับเพลงด้วยฟิลด์ position
กับกันเพลงซ้ำด้วย unique_together ครับ"

## สไลด์ 7 — Auth (~45 วิ)

"ฟอร์มสมัครสมาชิกสืบทอดจาก UserCreationForm ของ Django แล้วผมเพิ่มตรวจอีเมลซ้ำกับเบอร์โทร
รหัสผ่าน Django แฮชให้เอง ผมไม่เคยเห็นรหัสผ่านจริงของใคร
ย้ำอีกครั้งว่าสิทธิ์ตรวจที่เซิร์ฟเวอร์ทุกครั้ง ไม่ใช่แค่ซ่อนปุ่ม"

## สไลด์ 8 — CRUD + คิว (~1 นาที)

"CRUD มี 5 กลุ่มครับ ผู้ใช้ แนวเพลง แท็ก เพลย์ลิสต์ คิวเพลง
ทุกการลบมี popup ยืนยันก่อน
คิวเพลงทำได้ 4 อย่าง เพิ่มต่อท้าย เพิ่มขึ้นหน้า ย้ายลำดับ ติ๊กว่าเล่นแล้ว แล้วก็ล้างคิว
ลำดับเพลงในเพลย์ลิสต์เก็บด้วยฟิลด์ position ที่เล่าไปเมื่อกี้ครับ"

## สไลด์ 9 — ค้นหา YouTube (~1 นาที)

"การค้นหาใช้ YouTube Data API ครับ ส่ง regionCode เป็น TH กับหมวดเพลง
เพื่อให้ได้เฉพาะเพลงไทย และขอเฉพาะวิดีโอที่ฝังในเว็บได้
ผมใส่คีย์ไว้หลายตัว ถ้าตัวไหนโควตาหมดระบบสลับคีย์เองอัตโนมัติ
แล้วมีกรองซ้ำฝั่งเซิร์ฟเวอร์ 3 ชั้น คือวิดีโอที่โดนบล็อก ชื่อที่ดูเป็น AI
กับคลิปที่ไม่ใช่เพลงครับ
และถ้าโควตาหมดทุกคีย์ ระบบจะ fallback ไปค้นเพลงในฐานข้อมูลตัวเองแทน ไม่พังครับ"

## สไลด์ 10 — อัปโหลด + แบ่งหน้า (~45 วิ)

"รูปโปรไฟล์กับปกเพลงอัปโหลดได้ ตรวจขนาดไม่เกิน 2 MB รับเฉพาะ JPEG PNG WebP
เสิร์ฟไฟล์ผ่าน view ที่กัน path traversal คือเข้าถึงไฟล์นอกโฟลเดอร์ไม่ได้
การแบ่งหน้าใช้ Paginator ของ Django หน้าละ 20 รายการ มีปุ่มก่อนหน้า ถัดไป
หน้าสุดท้าย และใช้ร่วมกับช่องค้นหาได้"

## สไลด์ 11 — REST API (~45 วิ)

"API มีเกือบ 20 เส้นทางครับ แบ่งเป็น 4 กลุ่ม
กลุ่มค้นหา กลุ่มจัดการคิว กลุ่มสถานะเพลง กลุ่มเพลย์ลิสต์ เพลงของฉัน สถิติแดชบอร์ด
หน้าเว็บทั้งหมดคุยกับเซิร์ฟเวอร์ผ่าน API พวกนี้ด้วย fetch ไม่โหลดหน้าใหม่ครับ"

## สไลด์ 12 — แดชบอร์ด (~30 วิ)

"แดชบอร์ดมีการ์ดสรุป 4 ใบกับกราฟ 4 กราฟ คำนวณจากฐานข้อมูลจริงฝั่งเซิร์ฟเวอร์
ถ้าไม่มีข้อมูลกราฟจะว่าง ไม่แต่งตัวเลขครับ"

## สไลด์ 13 — ผลทดสอบ (~45 วิ)

"ผมเขียนเทสต์อัตโนมัติ 386 เคส แยก 25 โมดูล ผ่านทั้งหมดครับ
ครอบคลุมเส้นทางหลัก บัญชีทดสอบ สิทธิ์ตามบทบาท XSS สื่อ แดชบอร์ด
รันด้วยคำสั่งตามสไลด์ ได้ Ran 386 tests OK
และทดสอบด้วยมืออีก 20 กรณีตั้งแต่สมัครสมาชิกจนส่งออกข้อมูลครับ"

## สไลด์ 14 — ข้อจำกัด (~45 วิ — พูดอย่างมั่นใจ อย่าขอโทษ)

"ข้อจำกัดที่ผมทราบมี 4 ข้อครับ
ข้อแรกไฟล์ที่อัปโหลดบน Render ไม่คงอยู่ข้ามการ deploy เพราะดิสก์ชั่วคราว
ข้อสอง iOS กับ Safari บางเครื่องเล่นไม่ได้ หรือ Error 153 ผมมีโหมดสำรองให้แล้ว
**(โน้ต: สไลด์ข้อ SQLite กับ SECRET_KEY กับปุ่ม PDF แก้ไปแล้วตอนย้ายฐานข้อมูล
ถ้าอาจารย์ถามให้ตอบว่าแก้แล้ว — ดูโน้ตความจริงท้ายไฟล์)**"

## สไลด์ 15 — ภาคผนวก + จบ (~20 วิ)

"ลิงก์เว็บ QR GitHub กับบัญชีทดสอบอยู่สไลด์นี้ครับ
ขอบคุณครับ — พร้อมสาธิตระบบจริงครับ"

*(ต่อด้วยสาธิตสดตาม `docs/demo-rehearsal.md`)*

---

## โน้ตความจริง — สไลด์เก่าที่ต้องรู้ไว้กันตอบผิด

| สไลด์ 14 เขียนว่า | ความจริงวันนี้ |
|---|---|
| SQLite บนดิสก์ชั่วคราว ข้อมูลหายทุก deploy | ❌ เก่าแล้ว — ย้ายไป Postgres (Neon) ข้อมูลไม่หาย |
| SECRET_KEY เป็นค่าสำรองในโค้ด | ❌ เก่าแล้ว — ตั้งเป็น Environment บน Render แล้ว |
| ปุ่มส่งออก PDF ยังไม่ได้เชื่อมต่อ | ❌ เก่าแล้ว — ต่อแล้ว ใช้ `window.print()` กดแล้วเลือก Save as PDF ได้ |
| iOS Error 153 | ✅ ยังจริง — มีโหมดสำรองแล้ว |

> ถ้าอาจารย์อ่านสไลด์แล้วถาม ให้ตอบว่า "สไลด์ทำก่อนย้ายฐานข้อมูลครับ ปัจจุบันแก้แล้ว" แล้วชี้หลักฐาน (เว็บรันอยู่จริง ข้อมูลไม่หาย)
